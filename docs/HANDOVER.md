# 引き継ぎ・再実装

## 判断

- Sitesにまとめて公開するため、Go/Ginは初期実装に使わずTypeScriptを採用した。
- 時間の集計単位は暦日の00:00ではなく、ユーザーが設定する日の開始時刻。記録に開始時のルールを保存し、後の設定変更で過去の数字を変えない。
- 1作業の全時間を開始側の日に計上する。日付をまたいでも分割しない。
- 同時計測は1種類。履歴の時間重複も防止し、総計を実時間として扱う。
- 作業の削除はアーカイブ。記録と種類のIDは移行後も保持する。
- PCは丸いボタン、スマホは縦並びの長方形。説明文は必要な設定・エラーに絞る。

## Go/Ginなどで作り直す場合

1. 現アプリの設定から全データをJSONで書き出す。
2. `docs/API.md` / `lib/model.ts` / `lib/validation.ts` から新しいDBとインポーターを作る。ミリ秒はGoのint64で保持する。
3. 認証は新しい基盤で実装し、新アカウントと所有データを関連づける。Sites内のユーザーIDは他のSiteや新しい認証のIDと一致するとは限らない。
4. businessDay、dayStart、timezoneをそのまま移行する。開始時刻だけから現在の設定で全件再計算しない。
5. 移行中は旧アプリの計測を終了する。最終JSONを取り込んだ後、件数・種類別合計・深夜の所属日を比較する。
6. 新アプリでも「1ユーザーにつき計測中1件」のDB制約と書き込みの原子性を維持する。
7. `tests/core.test.ts` の境界値をGoのテストへ移植する。

## 制約・将来の拡張

- 終了忘れ通知は開いているブラウザで動く。タブを閉じた後にも配信する場合は、Web Push購読・サービスワーカー・サーバー側のスケジューラーを追加する。
- 初期実装は全記録を取得してブラウザで絞り込み・集計する。長年の大量記録では、DB側集計、履歴のAPIページング、ストリーミングエクスポートに移行する。
- JSON取り込みは16MB・20000記録・500種類を上限とする。それ以上の移行にはバックエンドの分割取り込みと処理状況の管理を追加する。
- インポートは同じIDのデータを上書きしない。双方向同期・競合解消は対象外。
- 夏時間の重複した現地日時は、入力の変換で選ばれた片方になる。移行JSONはUTCのため元の瞬間を失わない。
- 現在期間と前期間の比較は前期間全体を対象にする。経過日数で揃えた比較が必要なら別モードとして追加する。
- 所有者限定で公開する。複数人に提供する際はSitesの閲覧範囲を明示的に変更し、別ユーザーの認証で分離を確認する。

## 検証

`npm test` は日の区切り・うるう年・年またぎ・夏時間・24時間超・取り込み・重複を検証する。`npm run test:api` はローカルD1に対して認証、打刻切替、同時更新、再試行、修正・重複拒否、設定変更、復元を検証する。実際の本番データに対して実行しない。
