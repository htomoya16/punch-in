# 打刻の応答改善

2026-11-02。ローカルのビルド済みWorker / D1に約5,000記録を入れ、同じ端末で各6回計測した代表値。本番のインターネット遅延や端末性能を保証する値ではない。

| 項目 | 変更前 | 変更後 |
|---|---:|---:|
| 打刻の応答本文（開始） | 1,320,548 bytes | 323 bytes |
| リクエスト〜本文読み取りの中央値 | 188.6 ms | 18.6 ms |
| 通常打刻のDB往復 | 4回、履歴を前後で取得 | 2回、必要な行のみ |
| 変更のない定期取得の本文 | 全履歴 | 0 bytes（304） |

変更前は e7e162c の実装。変更後には検証用打刻が数件増えている。新旧応答形式の比較は `PERF_RECORDS=5000 npm run test:punch-api` で再現できる（新しい実装上で旧全体応答と差分応答を比較するため、変更前コードとの比較そのものではない）。

## 実装

- `lib/punch-server.ts`: 設定・対象作業・計測中・直近1件を1バッチで読み、楽観ロックと部分UNIQUE INDEXを維持したatomic batchで確定する。通常は全履歴を読まず、開始・終了した最大2件だけ返す。
- `lib/punch-state.ts`: 確定状態を変更せず仮表示する。成功後にrevisionが連続している差分だけ反映し、新しい状態を古い応答で戻さない。
- 押した直後に「保存中」を表示する。通信失敗は仮表示を外し、保存結果不明の再試行では同じmutationIdを使う。保存済みなのに応答だけ失われた場合も二重登録しない。
- クライアントはサーバー時計で補正した押下時刻を送る。サーバーが受信時刻の近傍で検証し、異常値・古い値は受信時刻に戻す。区間の順序も守る。
- 定期取得はrevisionを比較して未変更時304。非表示・保存中の取得を抑え、focus/visibilityイベントによる重複リクエストを減らす。
- 絞り込み・確定時間・カテゴリ別集計をメモ化する。毎秒は計測中の経過分を加え、完了したグラフは再描画しない。
- 0001のマイグレーションで(user_id, started_at)の索引を追加する。既存マイグレーションは変更しない。

## 確認

- 38件の単体テスト。差分・仮表示・競合時の原子性・再試行・押下時刻・日付境界を含む。
- 既存API20項目、新しい差分APIの同時更新・冪等性・旧形式互換・条件付き取得、ユーザー分離を確認。
- 実ブラウザの約5,000記録で、応答を待たせても約23msで保存中表示へ切り替わった。

## 残る範囲

初回読み込みと、他端末の変更があった時の全体更新では全記録を取得する。非常に多い記録ではDB側集計・履歴のページング・部分同期が次の改善候補になる。別端末との同時更新や応答欠落後の再試行では、整合性を優先して全体を再取得する場合がある。

## 日別メモ

メモは専用API・日付別CASで保存する。通常のstate・打刻差分には本文を含めず、自動保存時も打刻のrevisionを変えない。メモ用ストアとmemo化したエディターを分離し、毎秒の時計更新でエディターやMarkdownパーサーを再描画しない。エディターは初回に開いたとき、プレビュー用パーサーは初回プレビュー時だけ読み込む。

入力から800msのデバウンス、同じ日付につき1件の送信キューで保存をまとめる。下書きは150msでまとめてブラウザへ保存し、閉じる・離脱時は即時に保持する。保存中に追加入力があれば、先の版が確定してから最新本文を送る。メモの通信待ちで打刻ボタンを無効にしない。

単体テストは旧処理を含め48件、日別メモAPIは14項目、既存APIは20項目を確認。ブラウザではPC・390px幅で自動保存、再読込、プレビュー、履歴の日付選択、Escapeとフォーカス復帰、入力しながらの打刻を確認した。ローカルでの計測結果は実際の利用環境の遅延を保証する値ではない。

## 並行作業とテンプレート

並行作業の操作も履歴全体を読まず、対象記録・revision・対象作業の読取と、CAS付き書込の2バッチで差分を返す。初めて単独記録を並行形式へ変える際だけ、未保存の既存メモを先に確定する。画面には操作直後から仮の状態を表示する。

終了した記録の配分結果は不変なSessionオブジェクト単位で再利用し、時計更新ごとに全区間を走査しない。テンプレート管理はメモから開いたときに読み込み、打刻stateや定期取得へ本文を追加しない。

週表示では描画を7日分に限定し、各日の最初の40件以降は明示操作で追加する。週全体の空の日が表示されるため、履歴用の日別メモ全日付一覧の定期取得を省いた。設定一覧のドラッグはブラウザ内で表示順を更新し、ドロップ時だけ1回保存する。並び替え専用の追加依存パッケージは導入していない。


一括停止・再開も既存の差分APIと同じDBバッチ2回で確定する。クライアントの即時表示とサーバーの状態遷移は同じ関数を使い、通信待ちで時計が動き続けないようにする。集計の前期間分も終了済みの計上結果を再利用する。履歴の初期位置合わせは画面を開く・日付を選ぶときに限定し、定期取得や毎秒の時計更新では実行しない。


週タイムラインの区間モデルは週・データ・設定・フィルターが変わったときに計算する。終了済みの日は安定したpropsで再利用し、計測中の日の棒と小計だけを時計に合わせる。表示区間は各日160件・3レーン、グループ内の記録は50件、ホバー詳細は30件から追加表示する。作業記録が増えても、構造更新のメモ保持はJSON配列をIDで照合する1つのSQLにまとめ、ネスト深さが記録数で増えない。


## 記録一覧・日時ホイール・拡大タイムライン（2026-11-04）

- ホイールはスクロール中の中心行だけを描画フレームへまとめ、停止後160msで値を確定する。通常の時計更新では選択値やスクロール位置を初期化しない。入力フォーカスが外れる際も現在の中心を確定する。
- 終了済みのタイムライン日付行の再描画抑制と、計算済み配分の再利用は継続する。日別メモを開いて幅が変わった場合や拡大時は、横位置を時刻比率で復元する。
- 日時編集だけは別の親記録との重複確認を追加する。通常の打刻・一括停止・再開にDB往復を追加しない。今回のローカル打刻差分は321バイト、中央値約19ms、条件付きstateは304・本文0バイト。実環境の通信時間を示す測定ではない。

分単位への変更は表示・入力・CSVの整形に限定し、DB問い合わせ・打刻処理・配分計算を増やさない。タイムラインの目盛りはCSSの行と位置指定で分離し、毎秒の位置測定は追加しない。

時間・分の共通表示は小さな表示部品とCSSで処理し、追加の通信・計算用状態・位置測定を行わない。週タイムラインの終了済みの日付行の再描画抑制は維持する。
